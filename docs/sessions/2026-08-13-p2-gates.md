## 4. Full narrative response, verbatim

**All three verdicts change. That is the headline.**

| target | before | after | decided by |
|---|---|---|---|
| **Revenues** | `withheld_as_forecast` | **`publishable`** | every gate passed |
| **Expenditure** | `withheld_as_forecast` | **`withheld`** | accuracy vs the naive benchmark |
| **State budget balance** | `publishable` | **`withheld`** | accuracy vs the naive benchmark |

The project's only published forecast changes identity: it stops publishing the stock target, whose
error is 57.8% worse than repeating last week's same weekday, and starts publishing Revenues, which
is 24.2% better. Root **787 passed, 3 skipped**; frontend **110 passed**.

### 1. MASE is now a binding gate, at 1.0

The threshold is not a choice, and that is the point. MASE is the ratio of the model's error to a
seasonal-naive benchmark computed on TRAIN only, so **1.0 is the break-even where model and benchmark
are equally accurate.** Above it, a documented trivial alternative is more accurate, and there is no
reading under which the model's numbers are the best available estimate.

I deliberately added no safety margin. Setting 0.9 or 0.95 would have reintroduced exactly the
uncalibrated-constant problem this work exists to remove. The margin is *reported* instead
(`margin_pct`), so a model at 0.99 is visibly marginal rather than silently passing.

A MASE failure produces `withheld`, not `withheld_as_forecast`. The distinction matters:
`withheld_as_forecast` means "the numbers are the best central-tendency estimate available but we
cannot claim they anticipate events" — which was the right label for Revenues under the old gates.
When a naive benchmark is *more accurate*, that reading no longer holds, so the stronger label is
correct.

### 2. `vs_ruler` is demoted to a reported diagnostic

I replaced it rather than raising it, and the reason is in your own measurements. Its threshold was
`> 0%`, and a featureless constant — the TRAIN mean, no features, no model — scores **38.58%** on
Revenues and **35.69%** on Expenditure against that same ruler. So `> 0%` passes models far worse than
a constant.

It cannot simply be raised, because the constant's score is period- and target-dependent: the same
constant scores **−299.43%** on the stock target. Any single percentage would be meaningful for one
target and arbitrary for the other two. MASE does the same job properly — scale-free, comparable
across targets, and normalised by a benchmark computed on TRAIN only.

`skill_vs_ruler_pct` is still recorded and still shown, because it is the project's shared ruler and
the Forecast page plots it. It carries a caveat in the registry naming the constant's score, so nobody
reads 55.92% as strong evidence on a flow again.

### 3. The sentinel is calibrated: 1.50 → 1.15

I measured the null before touching the number, because guessing a replacement would have repeated the
original mistake. H0 is "the features carry no information about the target", and only the features are
nulled — the target is built exactly as the pipeline builds it and the split is the real TRAIN → DEV,
so anything the probe finds is an artifact of the instrument rather than the data. Two constructions:
`noise` (normal draws) and `permuted` (real feature rows shuffled, preserving marginals and
cross-correlation). The threshold is set from `permuted`, the wider and more realistic of the two.

**The null is tight around 1.00.** Pooled over 360 draws: median 1.0023, p99 1.0943, maximum 1.1164.

**The result inverts the complaint.** The concern was that 1.50 might be too lax. It is far too
strict: **its false-positive rate is 0.00%, and so is 1.12's.** A threshold sitting well beyond the
point where the FPR reaches zero buys no additional protection against noise — it only rejects real
readings. The prose rationale in `docs/SIGNAL_FINDING.md` described a margin of roughly 0.10 ("the
margin above 1.00 exists so that noise cannot pass"); the constant implemented one of roughly 0.50.

So `SENTINEL_MIN = 1.15` — the smallest round value with a measured 0.00% FPR over 360 draws, sitting
above the observed null maximum of 1.1164. The next lower round value, 1.10, has a measured FPR of
0.56%. The old value survives as `SENTINEL_MIN_UNCALIBRATED = 1.50` so the change is greppable.

Two readings change meaning once the null is known:

- **Revenues, 1.2255** is above the null's 99th percentile *and* above its observed maximum. Under
  1.50 this was "no signal". Measured against the null it is signal, at p < 1/360.
- **Expenditure, 1.0882** sits **below** the pooled null p99 of 1.0943. This is the more useful
  finding: its reading is not merely under a threshold, it is *inside the distribution that
  signal-free features produce.* "Indistinguishable from no information" is now a measurement, and the
  gate says so in those words.

And I did both halves of your option, not one: the threshold is calibrated **and** the sentinel is no
longer the sole publication gate, because MASE now binds alongside it. A single threshold deciding
publication alone is fragile even when calibrated.

The calibration is reproducible: `scripts/calibrate_sentinel.py` regenerates it, and a test asserts
the script exists and implements both nulls. A calibration nobody can re-run is just another
convention.

### The four verdicts stay four

Leakage, no-signal, persistence-mimicry and coverage remain four independent conditions with four
separate reason strings, asserted distinct. The accuracy gate is a **fifth** condition, not a merge:
a test shows a model that beats the naive benchmark while replaying persistence, and one that fails the
benchmark while carrying strong signal (which is precisely the stock target). Nothing collapses into
anything else. All failing reasons are reported, not only the deciding one — Expenditure fails two
gates and says so, because a reader fixing one should know about the other.

### The decision now lives in code, and the registry is its output

`registry/recipes.json` previously carried hand-written gate verdicts and a hand-written
`publication.verdict`, with the reasoning in a commit message. `publication_gates.py` is now the
reasoning, the registry is regenerated from it, and a test asserts the two agree. Each recipe records
its `superseded_verdict` and why, so the change is auditable rather than a silent rewrite. The
registry also gained a `gate_policy` block naming the thresholds, their rationale, and that
`vs_ruler_gated` is `false`.

### Three things the existing suite caught in my own work

Worth recording, because each was a real defect and none was mine to notice first.

**I wrote the acronym "MASE" into reader-facing prose.** `test_insights.py` and
`test_treasury_report.py` forbid jargon in what a Treasury reader sees, and they failed on my first
draft of `reason_plain`. Fixed by rewriting the reasons in plain language — *"Simply repeating what
happened on the same weekday last week is 10.4% more accurate than this model"* — and moving the
acronym to a technical `metric` field. The gate's `name` had the same problem, because the HTML report
renders it, so that is now "accuracy vs repeating the same weekday last week". I added a test that
asserts this at the source rather than only where it renders.

**`insights.py` hardcoded which targets are withheld.** Its headline paragraph opened *"For revenues
and expenditure, the system reports a typical level rather than a genuine forecast"* — false the moment
Revenues turned publishable. It now derives the names from the registry. A headline claim about which
lines are usable should never be a literal.

**A test encoded the old verdicts wholesale.**
`test_flow_targets_are_withheld_as_forecast_with_a_reason` asserted all three specific verdicts, which
made it a second copy of the registry rather than a check on it. Rewritten as the property it was
actually protecting — whatever the verdicts are, a failure is stated plainly, names a fix, and the
deciding gate is among the failures — with the verdicts themselves pinned once, in
`test_publication_gates.py`.

### One consequence to flag

The published issue at `forecasts/published/2025-08-06/` contains a **stock-target forecast whose
verdict is now `withheld`**, and a Revenues forecast labelled withheld that would now be publishable.
I did not rewrite it. A published issue is the immutable record of what was said on that date, and its
`gates.json` correctly records the verdict *at issue time*. The registry holds the current verdict.
Those can legitimately differ, and a consumer needs to know which is which — but nothing currently
reconciles them, which is the first thing I would fix next.

## 6. Outstanding

* **The published `2025-08-06` issue is not reconciled with the new verdicts.** Its `gates.json` holds
  the verdict at issue time, which is correct, but nothing tells a consumer that the current verdict
  for that target differs. This is the highest-value follow-up, and it decides what the Forecast page
  should show today.
* **No forecast has been re-issued under the new verdicts.** Revenues is now publishable and has never
  been published as such; the stock target is published and now withheld.
* **The MASE denominator is seasonal-naive with `season=5`**, chosen before this work and not
  revisited. A weekly season on a daily Treasury series is plausible but the gate now binds on it, so
  it deserves the same scrutiny the sentinel threshold just received.
* **The real sentinel readings are point estimates.** The null has 360 draws; each real reading has
  one, because the sentinel's internal target shuffle uses a fixed seed. A confidence interval on the
  real side needs the seed varied, which would let the gate state "signal detected at p < x" rather
  than a threshold comparison.
* **The calibration is specific to this data, h=5, and these three feature sets.** The script makes a
  re-run cheap; nothing forces one when a recipe changes.
* **`forecast_integrity.MIN_SIGNAL_RATIO` is still 1.5** and still used by the pipelines' own
  integrity reports. `publication_gates.SENTINEL_MIN` governs publication, so the two now disagree by
  design — the pipeline flags at 1.5, publication decides at 1.15. That is defensible but it is two
  numbers for one concept, and it should become one.
* Unchanged from earlier records: a data gap still becomes a training observation of `0.0` at the
  modelling layer; `conditional_coverage_gate` is not wired into `quantile_quality_gate`;
  `check_feature_leakage` is weak; only B_ML's selection path calls `assert_selection_free`; the four
  `is_stock` implementations diverge (latent); `a_stat_models_pipeline.py` is a second unreferenced
  A_STAT implementation; the committed 2026-08-04 a_stat leaderboard fails the contract (pre-existing);
  `⚡ Persistence (baseline)` uses decoration in a join key; ops P0, Phase-1 cleanup, registry approval
  workflow, single TEST read.
